From weather model to public product: building Garda Oracle

A MODEL IN A NOTEBOOK IS NOT YET A PRODUCT

The first version of Garda Oracle answered a modelling question: can the local Peler and Ora wind regimes at Lake Garda be predicted from large-scale weather data?

Once the answer looked promising, a different question became more important:

What would it take to turn that experiment into a small public application I would actually trust and use at the lake?

Putting a probability on a webpage is easy. Making sure that training, production, explanations, data licensing, and validation all describe the same model is the harder part.

DESIGNING FOR THE DECISION

At the lake, I do not want to inspect a machine-learning notebook. I want a quick answer for a specific decision: is Peler likely in the early morning, and is Ora likely in the afternoon?

Garda Oracle therefore shows two separate forecast cards for today, tomorrow, and the day after. Each card contains a GO, MAYBE, or NO GO assessment and the corresponding probability.

The distinction between Peler and Ora matters. They occur at different times, arrive from different directions, and respond differently to the weather situation. Combining them into a generic “wind forecast” would hide the question the model is actually trying to answer.

The interface is available in English, German, and Italian. It is deliberately compact enough for a phone, but it does not ask the user to trust a number blindly.

EXPLAINING A PROBABILITY

Opening a forecast card reveals the factors that move the model most strongly towards or away from a favourable outcome on that day.

Depending on the forecast, those factors may include the pressure distribution around the Alps, solar radiation, cloud cover, precipitation, humidity, or wind at 100 metres.

Because the underlying models are logistic regressions, these contributions can be calculated exactly. The application can show which standardised input values changed the model score most strongly.

That still does not prove causality. A contribution explains the model's calculation, not the atmosphere itself. The interface therefore describes both the physical interpretation of a factor and the limits of the explanation.

Explainability here is not a decorative chart added after training. It is a consequence of choosing a model and pipeline whose calculations can be traced from input to output.

ONE FEATURE PIPELINE, NOT TWO

One of the easiest ways to introduce silent errors into a machine-learning product is to calculate features differently during training and production.

A pressure difference might use another station order. A time window might be shifted by an hour. Missing values might be handled differently. The model would still return a probability, but it would no longer be the model that was evaluated.

Garda Oracle avoids this by using the same feature builder for offline training and the live website. Time windows, pressure differences, and derived weather signals are implemented once.

A golden-vector test adds another guardrail: one known input is paired with its expected model output. If an implementation change silently alters the calculation, the test fails.

This is less visible than the forecast cards, but it is one of the most important parts of the system.

A SMALL PRODUCTION RUNTIME

The models are trained offline with scikit-learn. The public service does not need to carry the training stack with it.

Means, standard deviations, coefficients, calibration parameters, and decision thresholds are exported as plain Python data. At runtime, inference is reduced to scaling the inputs, calculating a dot product, and applying a logistic function.

The deployed application therefore needs neither scikit-learn nor pandas nor NumPy.

The rest of the stack is intentionally modest:

• FastAPI and Jinja2 for the application
• Open-Meteo for forecast fields
• Meteotrentino station T0193 for current and historical observations
• a 30-minute cache for forecasts and a five-minute cache for live wind
• Cloud Run as a stateless service

Keeping the runtime small reduces deployment complexity without changing the evaluated model.

OPEN SOURCE MEANS MORE THAN PUBLISHING CODE

Making the repository public required more than choosing a licence and writing a README.

The project documents the licences and attribution requirements of its data sources. Raw source datasets are not committed to the repository. Instead, the repository provides a reproducible path for fetching data, deriving Peler and Ora labels, training the models, validating them, and exporting the serving parameters.

The model card records not only performance but also limitations and negative results. A single measurement station in Torbole cannot represent the entire northern lake. Historical labels describe wind direction and average speed, not gust quality or whether a session was safe. The output is not an official weather or safety forecast.

These constraints are part of the product, not footnotes to hide after deployment.

WHAT I TOOK AWAY FROM THE PROJECT

Five lessons from building Garda Oracle have become particularly useful to me:

1. Start with a precise local decision, not with a model architecture.

2. Test whether a signal survives the move from reconstructed weather to real forecast inputs.

3. Explainability starts with a consistent data pipeline, not with a tooltip.

4. Data licensing and reproducibility are architectural concerns.

5. A small, transparent model with honest validation can be more useful than a more complex system whose behaviour is difficult to trace.
